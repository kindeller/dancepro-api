# ADR-0011: Programme drafts and confirmed preparation snapshots

## Status

Accepted for the first programme preparation slice, 21 September 2026.

## Context

Competition and concert programmes have different structures. Source PDFs may
contain columns, repeated numbering, class-only labels, nonconsecutive event days,
and cast information that is not a running order. Automated extraction must feed
an editable draft rather than immediately controlling media routing.

The existing scheduling event already supports multiple days through shifts.
Existing booking programme replacement removes the old attachment. A confirmed
preparation therefore cannot rely on that mutable attachment path.

## Decision

Implement the feature under `app/Features/Programmes`, with one programme per
existing scheduling event. Keep the current event-code calculation.

Use four tables:

- `programmes`: event relationship, current source, optimistic draft version and
  last editor/time.
- `programme_nodes`: stable UUID records with a fixed kind, ordered current draft
  data and an active flag. Removal from a draft deactivates the record; it does
  not delete the identity. UUIDs may be generated by the editor, but the server
  validates hierarchy, uniqueness and ownership. UUIDs confer no authorisation.
- `programme_sources`: retained private PDF copies, uploader and creation time.
  Replacements keep older sources. The first preparation copies the current
  event PDF if it exists; new uploads use the existing malware scanner.
- `programme_revisions`: immutable application snapshots keyed by programme and
  draft version, with the confirming actor/time and retained source reference.

The first node kinds are deliberately limited: competition day/section/item and
concert group/item. Type-specific draft fields live in JSON while public identity,
ownership, kind, ordering and active state are normal columns. This avoids separate
nearly identical draft/revision tables per programme shape. Future commerce/media
relationships must reference stable records; they must not join on names, numbers
or JSON array positions. This slice does not create those media relationships.

Save, source replacement and confirmation lock the programme row and check the
submitted draft version. Concurrent stale mutations return HTTP 409. Confirmation
of the same version is idempotent. Draft edits leave the last confirmed snapshot
unchanged. Hierarchy is validated when saving; required titles/dates/numbers and
number conflicts are checked when confirming. Competition section numbers are
unique across an event because recorder filenames identify event/section/competitor;
competitor numbers are unique within a section. Concert printed numbers can repeat.

A confirmed snapshot includes schema version, event UUID/code/name/type, programme
UUID/version, source UUID and ordered nodes with parent UUIDs. The response adds
revision UUID, confirmation time and an authenticated source URL pinned to that
revision. Fetching the source after a newer confirmation cannot silently return a
different PDF. Staff access and explicit `programmes:read` token ability are both
required for the preparation API. No crew assignment or selected upload role is
required in this initial staff-only contract. Delegated crew permissions remain a
later permission-matrix slice. No internal event notes or storage keys are exposed.

## Alternatives considered

- Reparse the PDF on demand: rejected; extraction is uncertain and offline
  preparation must be deterministic.
- Use filenames/numbers as identity: rejected; names, ordering and some displayed
  numbers can change without transferring media ownership.
- Update the confirmed structure in place: rejected; an uploader may already
  have prepared an earlier version.
- Store only a JSON document: rejected; stable retained node records are needed
  as a future relational target.
- Fully normalise every draft/revision field now: deferred; the small bounded
  draft schema is easier to evolve while validating the real programmes. Reporting
  or media assignment requirements may justify additional typed tables later.

## Consequences and limits

The editor is manual, with bulk paste and protected PDF preview. It does not yet
extract, OCR, reconcile document changes, make folders or upload media. Source
replacement intentionally does not overwrite event/booking/customer programme
attachments; its role is preparation evidence only.

All confirmed versions retain their structures and PDFs. Draft saves record the
latest editor/time, not a full per-keystroke audit. There is no history deletion
endpoint. Filesystem writes cannot share the database transaction: if persistence
fails after a copy/upload, an unreferenced private file can remain. Do not introduce
automatic destructive storage cleanup; address retention/reconciliation explicitly
in a later storage task.

No publication, payment, schedule, approval or media-release status is changed by
programme confirmation. Source dates/session labels are manually reviewed context,
not instructions to reschedule crew. Missing source PDFs do not block manual entry.

Rollback drops only the four new tables and their dependency links in reverse
order. Rolling back after real use destroys programme history; retained PDF files
are deliberately not deleted. Rollback/reapply was verified while the local
programme tables were empty.
